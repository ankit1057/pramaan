The story

In 1953, Hans Peter Luhn, an IBM researcher working on chemical information retrieval systems, filed an internal memorandum proposing an ingenious solution for organizing chemical formulas. Standard alphabetical card sorting required tedious manual indexing and $O(N)$ sequential scans. Luhn proposed mapping alphanumeric text strings into short numerical bucket addresses by summing characters and extracting numerical moduli. He had invented the hash table. Decades later, hash tables became the workhorse of modern software engineering: dictionaries, database indexes, cryptographic caches, and memory deduplication engines depend entirely on hashing. However, hashing is not magic: poor hash distributions trigger catastrophic hash collisions that degrade $O(1)$ operations into $O(N)$ linked-list crawls, malicious collision attacks can crash web servers, and distributed systems require consistent hashing to survive server node failures.

Say it simply

A hash table is like a giant library where every book has a magic code that tells you the exact shelf number where it belongs. Instead of searching through every book one by one, you compute the book's hash code, jump straight to that shelf, and find the book immediately in $O(1)$ constant time. If two different books happen to get assigned to the same shelf (a collision), the table handles it by chaining them in a small list or searching for the next empty shelf (linear probing). Hash tables also power Bloom filters (super-compact probabilistic filters that instantly tell you if an item definitely doesn't exist) and consistent hashing (which distributes data across thousands of cloud servers).

Say it precisely

Hashing architectures balance uniform key distribution, collision resolution, and memory overhead: 1. Collision Resolution Strategies: - Separate Chaining: Each bucket maintains a linked list or red-black tree (e.g. Java 8+ HashMap). - Open Addressing (Linear Probing): All entries live directly in the primary array. On collision at index $h$, probe sequentially: $h + 1, h + 2, \dots \pmod M$. Deletions require placing tombstones (DELETED) to prevent breaking probe search chains!

  1. Load Factor ($\alpha$) & Resizing: - $\alpha = \frac{N}{M}$ where $N$ is element count and $M$ is bucket capacity. - For open addressing, $\alpha$ must strictly stay below $0.75$ (as $\alpha \to 1$, clustering causes probe lengths to explode). - When $\alpha \ge \alpha_{\text{threshold}}$, allocate buffer of capacity $2M$, rehash all active entries, and discard tombstones.

  2. Bloom Filters: - Space-efficient probabilistic data structure representing a set of $N$ items in $M$ bits using $K$ independent hash functions. - Operations: add(x) sets bits $h_1(x), \dots, h_K(x)$ to 1; contains(x) checks if all $K$ bits are 1. - Properties: Zero false negatives (if contains returns False, item is definitely not in set); false positive probability: $$p \approx \left(1 - e^{-KN/M}\right)^K$$ Optimal number of hash functions: $K = \frac{M}{N} \ln 2$.

  3. Consistent Hashing: - Maps both server nodes and data keys onto a virtual ring $[0, 2^{32}-1]$ using cryptographic hashes (e.g. SHA-256). - A key is assigned to the first server encountered moving clockwise on the ring. - Adding or removing a server node redistributes only $\approx \frac{1}{N_{\text{nodes}}}$ of total keys, avoiding full cluster cache invalidation.

Why it's true

To understand why tombstones are mandatory in open addressing with linear probing, trace what happens during deletion: Suppose array size is 5 and keys hash as follows: - hash("A") = 1 -> stored at slot 1. - hash("B") = 1 -> collides at 1! Probes to slot 2 and stores at 2. - hash("C") = 1 -> collides at 1 and 2! Probes to slot 3 and stores at 3. The array contents: [None, A, B, C, None].

Now, suppose you delete key "B". If you naively set slot 2 to None: [None, A, None, C, None] What happens when a caller queries get("C")? 1. Computes hash("C") = 1. Slot 1 contains "A" $\ne$ "C". 2. Probes to slot 2. Slot 2 is None! 3. Standard linear probing halts search upon encountering None (assuming no further elements exist). 4. get("C") returns NotFound, even though "C" is present at slot 3!

By replacing deleted entries with a special tombstone sentinel (DELETED): [None, A, DELETED, C, None] The search probe for "C" encounters DELETED, recognizes that the probe chain continues, checks slot 3, and successfully finds "C"! During subsequent insertions, new keys can overwrite tombstones, reclaiming memory.

Warm-up
Rabin-Karp polynomial rolling hash substring search algorithm

not tried


Write rabin_karp_search(pattern, text, prime_mod=1000000007, base=256):
Inputs:
- pattern: String search target (length $M$).
- text: String source text (length $N$).
- prime_mod: Large prime modulus (default 1000000007).
- base: Integer alphabet radix (default 256).


Algorithm Protocol:
1. If $M > N$ or $M == 0$: return [].
2. Compute h_multiplier = pow(base, M - 1, prime_mod).
3. Compute initial polynomial hash for pattern and first window of text ($0 \le i < M$):
   $$\text{hash} = \sum_{i=0}^{M-1} \text{ord}(s[i]) \times \text{base}^{M - 1 - i} \pmod{\text{prime\_mod}}$$
4. Slide window across text ($j \in [0, N - M]$):
   - If window_hash == pattern_hash:
     Verify exact substring equality text[j:j+M] == pattern (guarding against hash collisions). If matches, record index $j$.
   - If $j < N - M$:
     Roll hash forward in $O(1)$ time:
     $$\text{new\_hash} = ((\text{old\_hash} - \text{ord}(text[j]) \times \text{h\_multiplier}) \times \text{base} + \text{ord}(text[j + M])) \pmod{\text{prime\_mod}}$$
5. Return list of matching start indices.

    Write a class LinearProbingHashTable:
Implement an open addressing hash table:
1. __init__(self, initial_capacity=4, max_load_factor=0.70):
   - Initializes table array of length initial_capacity with None.
   - Tracks active element count size = 0.
2. put(self, key, value):
   - Hash index: idx = hash(key) % capacity.
   - Linear probe until finding matching key (update value), a None slot, or a "TOMBSTONE" slot.
   - Insert key-value pair (key, value). Increment size += 1 if new key.
   - If load factor size / capacity >= max_load_factor:
     Resize table to double capacity (2 * capacity), rehash all active entries, and discard tombstones!
3. get(self, key):
   - Probe starting from hash(key) % capacity.
   - If key found: return value.
   - If encounter None: key does not exist, return None.
   - Skip past "TOMBSTONE" entries without stopping!
4. delete(self, key):
   - Find key. If present, replace slot with "TOMBSTONE", decrement size -= 1, and return True.
   - If not found, return False.

      Write a class BloomFilter:
Implement a probabilistic Bloom filter:
1. __init__(self, bit_array_size=64, hash_count=3):
   - Initializes bit array bits = [0] * bit_array_size.
   - Stores m = bit_array_size and k = hash_count.
2. _hash(self, item, seed):
   - Computes deterministic hash index:
     int(hashlib.md5(f"{seed}:{item}".encode('utf-8')).hexdigest(), 16) % self.m.
3. add(self, item):
   - Computes $K$ hash indices for $i \in [0, K-1]$ using seed = i.
   - Sets self.bits[index] = 1 for each hash index.
4. contains(self, item):
   - Computes $K$ hash indices for $i \in [0, K-1]$.
   - Returns True if ALL $K$ bit positions are 1.
   - If any bit position is 0, returns False (guaranteeing zero false negatives!).
5. theoretical_false_positive_rate(self, item_count):
   - Returns float: $\left(1 - e^{-k \cdot n / m}\right)^k$ where $n = \text{item\_count}$.

        Write a class RandomizedSet:
Implement a collection supporting $O(1)$ average time complexity for all three operations:
1. __init__(self):
   - Initializes dynamic array elements = [] to store values for $O(1)$ random indexing.
   - Initializes dictionary val_to_index = {} mapping val -> array_index.
2. insert(self, val):
   - If val already in set: return False.
   - Append val to elements.
   - Record val_to_index[val] = len(elements) - 1.
   - Return True.
3. remove(self, val):
   - If val not in set: return False.
   - $O(1)$ Deletion Strategy:
     - Find index of val: idx = val_to_index[val].
     - Get last element in elements: last_elem = elements[-1].
     - Swap last_elem into slot idx:
       elements[idx] = last_elem
       val_to_index[last_elem] = idx
     - Pop last element from elements: elements.pop().
     - Delete val from val_to_index: del val_to_index[val].
   - Return True.
4. get_random(self, random_func=None):
   - Returns a uniformly random element from elements in $O(1)$ time.
   - If random_func provided, call random_func(elements). Else use elements[0] if length 1.

          Misconceptions
            

          • "Hash table lookups are always guaranteed to be O(1) in the worst case." In the worst case where all keys collide in the same bucket, lookups degrade to linear O(N) time; expected O(1) relies on uniform hash distribution.
            • 

          • "Deleting from an open addressing hash table can just set the slot to None." Setting a slot to None breaks linear probe search chains; tombstones (DELETED markers) are mandatory to allow ongoing searches to continue past deleted entries.
            • 

          • "A Bloom filter can produce false negatives." Bloom filters mathematically guarantee zero false negatives; if an item was added, all its hash bits will always remain 1.
            • 

          • "Consistent hashing requires rehashing all keys when adding a new server." Consistent hashing places nodes on a ring; adding a node redistributes only a small fraction of keys (~1/N), leaving the rest untouched.
            • 

          Where it breaks
          Hashing architectures break down when malicious users exploit known polynomial hash coefficients to generate worst-case collision attacks that degrade hash tables into $O(N)$ linked lists, triggering denial-of-service freezes, when linear probing tables omit tombstones and cause existing keys to become unfindable after deletions, or when Bloom filters exceed capacity thresholds, causing false positive rates to approach 100%.
          In your real work
          Hashing structures underpin offline-first data management on mobile devices. A Bloom filter gives $O(1)$ pre-filtering before touching a local encrypted SQLite store, a randomised-set structure supports unbiased sampling of inspection records in constant time, and rolling hashes accelerate duplicate-document detection during a high-volume batch intake.
          Flash cards
          What is the difference between separate chaining and open addressing?
          Separate chaining stores collisions in external linked lists; open addressing probes for the next available slot within the primary array.
          Why are tombstones necessary in linear probing hash tables?
          To prevent probe chains from terminating prematurely when searching for elements inserted after a deleted key.
          What is a Bloom filter and what guarantees does it make?
          A space-efficient probabilistic set that guarantees zero false negatives, though it may produce false positives.
          How does RandomizedSet achieve O(1) deletion?
          By swapping the element to be deleted with the last element of a dynamic array, updating its index in a hash map, and popping the last element.
          What is the Rabin-Karp algorithm?
          A string-searching algorithm that uses polynomial rolling hashes to compare substring hashes in O(1) time per window step.
          What is consistent hashing?
          A hashing technique mapping keys and servers onto a virtual ring so that adding/removing nodes rehashes only a minimal fraction of keys.
          Stop when
          You can implement Rabin-Karp rolling hash searches, build open addressing hash tables with tombstones, calculate Bloom filter false-positive bounds, and implement O(1) RandomizedSet collections.
