The story

In 2023, open-source developers achieved a long-sought holy grail: running a 7-billion parameter language model locally on an ordinary commercial smartphone without an active cellular or internet connection. For years, conventional wisdom asserted that large models were strictly the domain of multi-GPU cloud datacenters consuming thousands of watts of power. But when Apple Silicon unified memory architectures and Qualcomm Snapdragon neural processing units (NPUs) brought high-speed memory buses and dedicated tensor acceleration to mobile chipsets, edge inference became a viable engineering discipline. Yet running an LLM on a battery-powered device presents ruthless physical realities: Android's Low Memory Killer (LMK) will brutally terminate any background process that exceeds strict RAM thresholds, mobile memory bandwidth is a fraction of datacenter HBM, and sustained inference quickly turns aluminum phone casings into hand-warmers, triggering severe CPU thermal throttling that collapses decoding throughput.

Say it simply

Running a large language model directly on a smartphone lets you use AI privately and offline, but mobile phones have strict hardware limitations. A phone shares a small pool of memory between the operating system, camera, user apps, and the AI model. To prevent the phone from crashing or running out of memory, models use memory-mapping (mmap) so weights are loaded on demand rather than all at once into RAM. Developers must carefully balance processor power across big and little battery-saving CPU cores, manage thermal heat buildup so the phone does not throttle down its speed, and measure battery energy consumed per generated word.

Say it precisely

  1. The Tiny Backpack (Memory Budget): A phone is like a small backpack. You have to fit the robot's giant rulebook (weights), its sticky notes for the current conversation (KV cache), and its scratch paper for math (activations) all in one small bag without tearing it!
  2. The Strict Bouncer (Low Memory Killer): A phone has a strict bouncer watching the memory. If the robot takes up too much room, the bouncer instantly kicks the robot out so the phone can still receive text messages and take photos. To sneak past the bouncer, the robot leaves its giant rulebook in the trunk of the car and only runs out to read one page at a time.
  3. The Tiny Straw (Memory Bandwidth): A phone's brain is super fast, but it drinks information through a very tiny straw. No matter how fast the brain can think, it can only talk as fast as the words can travel up the skinny straw.
  4. The Two-Speed Bicycle (Big and Little Cores): A phone has giant power-hungry gears (big brains) and tiny battery-saving gears (little brains). If you accidentally hand a giant math problem to a little battery-saving brain, the entire robot gets stuck waiting for it to finish!

Why it's true

Why is running an AI on a phone so much harder than a giant cloud computer?

  1. The Olympic Sprinter: Imagine an Olympic sprinter waiting for a tiny toy train to deliver their running shoes. A modern phone brain can do 45 trillion math problems a second, but it actually spends 99 percent of its time completely bored and asleep, just waiting for the tiny memory straw to deliver the numbers!
  2. The Sweat Problem (Thermal Throttling): Big cloud computers have giant spinning fans and water coolers. Phones have absolutely nothing! If the robot works super hard for two straight minutes, the phone gets dangerously hot. To stop the glass from burning your fingers, the phone hits the emergency brake and forces the robot to work half as fast to cool down.
  3. The Practice Lap (Honest Testing): When scientists test how fast a robot is, they never count the very first run! The robot is just waking up, stretching, and finding its tools. To measure a phone fairly, you have to let the robot do a few warm-up laps, test it 50 times, and check exactly how much juice it drains from the battery on every single word.

Write calculate_mobile_memory_budget(params_b, bits_per_param, context_len, num_layers=32, hidden_dim=4096, lmk_limit_gb=5.0):
Compute exact memory components for an on-device deployment:
1. weights_gb = params_b * (bits_per_param / 8.0).
2. kv_cache_gb = 2 * num_layers * hidden_dim * context_len * 2 / 1e9 (in FP16 bytes).
3. activation_scratch_gb = 2 * hidden_dim * context_len * 2 / 1e9.
4. os_runtime_overhead_gb = 0.35 GB.
5. total_rss_gb = sum of all 4 components.
6. is_safe = Boolean True if total_rss_gb <= lmk_limit_gb else False.
7. Return dictionary with all 6 keys rounded to 3 decimal places (except is_safe).

    Write simulate_mmap_access(page_requests, max_resident_pages):
Simulate OS page cache management for memory-mapped model weights using an LRU (Least Recently Used) cache:
Inputs:
- page_requests: List of integer page IDs requested in chronological order during layer execution.
- max_resident_pages: Integer maximum number of physical RAM pages allowed in page cache before eviction.
    

    Requirements:
1. Maintain current resident pages in memory (up to max_resident_pages).
2. For each requested page:
   - If page is already resident: record a "hit" and refresh its LRU position.
   - If page is not resident: record a "fault". If cache is full, evict the least recently used page, then insert new page.
3. Compute hit rate: hits / total_requests (if page_requests empty, hit rate is 1.0).
4. Return dictionary:
   {"total_requests": int, "page_faults": int, "page_hits": int, "hit_rate": round(rate, 4), "final_resident_pages": list_of_ints_in_mru_order}.

    pages = [1, 2, 3, 1, 2, 3] # Cache size 3
    res = simulate_mmap_access(pages, 3)
    assert res["page_faults"] == 3

    assert set(res["final_resident_pages"]) == {1, 2, 3}

def test_mmap_lru_eviction():
    pages = [1, 2, 3, 4] # Cache size 2
    # 1 in -> [1]
    # 2 in -> [1, 2]
    # 3 in -> evicts 1 -> [2, 3]
    # 4 in -> evicts 2 -> [3, 4]
    res = simulate_mmap_access(pages, 2)
    assert res["page_faults"] == 4
    assert res["page_hits"] == 0
    assert res["final_resident_pages"] == [4, 3] # MRU order

def test_empty_requests():
    res = simulate_mmap_access([], 5)
    assert res["hit_rate"] == 1.0
    assert res["page_faults"] == 0

      Write calculate_decode_throughput_under_thermal(model_weights_gb, mem_bandwidth_gb_s, elapsed_seconds, throttle_schedule):
Inputs:
- model_weights_gb: Size of model weights in GB (float).
- mem_bandwidth_gb_s: Peak memory bandwidth in GB/s (float).
- elapsed_seconds: Continuous runtime duration in seconds (float).
- throttle_schedule: List of tuples (threshold_seconds, throttle_ratio) sorted by threshold_seconds ascending.
  - E.g., [(60, 0.15), (180, 0.35), (300, 0.50)] means:
    - If elapsed < 60: throttle = 0.0
    - If 60 <= elapsed < 180: throttle = 0.15
    - If 180 <= elapsed < 300: throttle = 0.35
    - If elapsed >= 300: throttle = 0.50
      

      Requirements:
1. Base unthrottled throughput: mem_bandwidth_gb_s / model_weights_gb (tokens per second).
2. Determine current throttle ratio based on elapsed_seconds.
3. Effective throughput: base_throughput * (1.0 - throttle_ratio).
4. Energy consumption in Joules:
   - Assume baseline SoC power is 4.5 Watts unthrottled, scaling down with clock frequency:
     Active power: 4.5 * (1.0 - 0.7 * throttle_ratio).
   - Total energy per token: active_power / effective_throughput (in Joules per token).
5. Return dictionary:
   {"base_tokens_sec": round(T_base, 2), "effective_tokens_sec": round(T_eff, 2), "throttle_ratio": float(throttle_ratio), "energy_per_token_joules": round(E_token, 4)}.

Inputs:
- latencies_ms: List of positive float latency measurements in milliseconds.

          Misconceptions
            

          • "Edge LLMs can be evaluated accurately using single run averages." Single run measurements are heavily corrupted by cold-start page faults and OS background preemption; robust benchmarks require warmup exclusion and reporting P50/P90/P99 percentiles.
            • 

          • "More CPU threads always make mobile LLM inference faster." Mobile chips feature heterogeneous cores; allocating more threads than big cores forces synchronization barriers across slow efficiency cores, reducing throughput and inflating thermal throttling.
            • 

          • "Virtual memory size (VMS) represents the actual RAM consumed by the app." Virtual size counts mapped address space, but memory-mapped model weights only occupy physical RAM (RSS) as individual 4KB pages are touched.
            • 

          • "A mobile NPU's advertised TOPS capacity determines its generation speed." Autoregressive generation is strictly bounded by memory bandwidth; a 45 TOPS NPU will still decode at 15-25 tokens/sec if memory bus bandwidth is 60-80 GB/s.
            • 

          Where it breaks
          Mobile LLM execution breaks down when concurrent camera or audio background tasks trigger Android LMK termination due to cumulative RAM exhaustion, when prolonged continuous inference elevates battery temperatures above safety limits (exceeding 45 degrees Celsius), forcing hard emergency CPU thermal down-clocking, or when unaligned memory-mapped binary reads incur catastrophic page fault overhead on flash storage.
          In your real work
          Edge AI runtimes such as ExecuTorch, MLC-LLM and the llama.cpp Android ports are engineered around mobile memory and thermal budgets. Weights are mapped read-only with mmap and aggressively block-quantised to 4 bits, so a handset can run multimodal inference offline without the battery drain a naive full load would cause.
          Flash cards
          What four components comprise an on-device LLM memory budget?
          Model weights, Key-Value (KV) cache, activation scratch buffers, and runtime heap/system overhead.
          Why does mmap prevent Android Low Memory Killer (LMK) termination?
          Memory-mapped weights reside in the clean OS page cache backed by disk and can be dropped without swapping under memory pressure, keeping RSS low.
          Why is autoregressive decoding memory-bandwidth bound on mobile SoCs?
          Because loading 3.5 GB of weights for every single decoded token saturates the 60-80 GB/s memory bus long before NPU compute units are fully utilized.
          What happens during mobile thermal throttling?
          SoC governors reduce CPU and NPU clock frequencies by 30% to 50% to prevent chassis overheating, causing token generation speed to collapse.
          Why must warmup runs be excluded from mobile latency benchmarks?
          To eliminate one-time cold-start overheads such as file loading, dynamic linking, and memory allocation from steady-state performance metrics.
          What is the difference between ARM big and LITTLE cores?
          Big cores maximize clock speed and single-thread throughput for compute bursts; LITTLE cores maximize energy efficiency for background tasks.
          Stop when
          You can calculate mobile RAM budgets against LMK thresholds, explain memory-bandwidth decode limits, and implement honest percentile latency benchmarking.
