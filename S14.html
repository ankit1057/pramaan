The story

In 2017, enterprise software engineering confronted a painful mobile deployment reality: business rules, compliance workflows, and regulatory field forms changed on a weekly basis, while mobile app store review cycles and user update adoption took weeks or months. If a government tax regulation altered a mandatory field or added an agricultural inspection rule, mobile teams could not afford to ship a full binary update to Google Play and Apple App Store for every minor form modification. The industry converged on a transformative architectural pattern: Server-Driven UI (SDUI). Instead of hardcoding UI layouts and business validation in client binaries, the server delivers declarative JSON schemas defining field types, dynamic visibility rules (depends_on), validation scripts, and workflow transitions. The mobile client acts as a high-performance native rendering engine and script evaluator, dynamically instantiating widgets, evaluating expressions, and executing client-script hooks with zero client-side binary recompilation.

Say it simply

Server-Driven UI (SDUI) lets you change how a mobile app looks and behaves without releasing a new app store update. Instead of programming buttons, text fields, and dropdowns directly into the app code, the server sends a JSON blueprint that says: "show a text field for the sender name, and if the category is electronics, show a humidity percentage slider." The mobile app reads this blueprint, displays the right native widgets, and checks validation rules dynamically. If a rule changes tomorrow, the server updates the blueprint, and every user's app immediately reflects the new form fields and rules on their next screen refresh.

Say it precisely

Server-driven UI and dynamic form architectures require strict declarative schema semantics and isolated expression execution: 1. Schema-Driven Field Rendering: - Schemas map field types (Data, Int, Float, Select, Check, AttachImage, Table) to platform-native widgets. - Dynamic Metadata: - depends_on: Condition string determining whether the field is visible in the UI. - mandatory_depends_on: Condition string determining whether the field is required before form submission. - read_only_depends_on: Condition string determining whether the field is locked against user input.

  1. Safe Subset Expression Evaluation: - Evaluating arbitrary JavaScript or Python strings on mobile introduces remote code execution (RCE) vulnerabilities. - Dynamic expressions are evaluated using a sandboxed Abstract Syntax Tree (AST) evaluator supporting only safe operators: $$\text{Expr} \in \{ ==, !=, <, <=, >, >=, \text{in}, \&\&, ||, ! \}$$ accessing only authorized form state dictionaries (doc.field_name).

  2. Client-Script Hook Lifecycle: - Forms execute event lifecycle hooks:

    • onload: Triggered when form schema is first loaded into memory.
    • refresh: Triggered whenever form state is repainted.
    • validate: Triggered prior to form submission; can cancel commit by throwing a ValidationError.
    • field_change: Triggered when a specific input field value changes, triggering cascading visibility recalculations.

  3. Differential Parity Oracle & Reference Shim: - When migrating web-based ERP systems (like Frappe) to Flutter or native Android, the mobile implementation must achieve exact parity with the reference platform. - The 'Superset, Never Contradicting' Criterion: The mobile client may provide richer features (e.g. offline caching), but must NEVER contradict the server's validation outcomes. - If an expression invokes missing client stubs, the differential oracle returns "INCONCLUSIVE" rather than an incorrect pass or fail.

Why it's true

To understand why expression evaluation must be restricted to a safe AST subset, consider what happens if a mobile client uses eval() or an embedded JavaScript engine to execute server-delivered visibility strings:

// Malicious or corrupted expression payload delivered over network:
doc.category == 'electronics' && (function(){ stealLocalKeys(); return true; })()

If dynamic forms use raw string evaluation, compromised backend APIs or Man-in-the-Middle network attackers can execute arbitrary code inside the mobile application sandbox! Restricting expression parsing to a tokenizer and AST validator guarantees that only authorized document fields and logical comparisons are computed.

The Inconclusive Stub Problem in Parity Testing: When building mobile clients that replicate Frappe or web form behavior, engineers write differential test harnesses that execute test payloads simultaneously through the backend Python engine and the mobile Dart client. If the mobile client encounters a custom server API call that has no client-side stub: - Treating the missing stub as false causes incorrect validation failure. - Treating the missing stub as true bypasses mandatory security checks. The differential oracle must explicitly mark the test result as INCONCLUSIVE, alerting developers that an essential stub must be implemented before parity can be certified.

Write evaluate_depends_on(expression_str, form_doc):
Inputs:
- expression_str: String boolean expression referencing document fields:
  - Examples: "eval:doc.category == 'electronics'", "eval:doc.weight_kg >= 100", "eval:doc.status in ['Draft', 'Pending']".
  - Also handles plain field truthiness: "doc.has_humidity" (true if truthy in form_doc).
  - If expression_str is None or empty: returns True (always visible/mandatory).
- form_doc: Dict containing current form state {"category": "electronics", "weight_kg": 120, ...}.


Rules:
1. Strip leading "eval:" if present.
2. Safe Evaluation:
   - Only allow access to fields in form_doc via doc.<fieldname>.
   - Support operators: ==, !=, <, <=, >, >=, in.
   - Disallow any dangerous python primitives (__import__, open, exec, eval).
3. Return boolean True or False.

      Write a class ClientScriptDispatcher:
Manage and execute form client scripts:
1. __init__(self):
   - Initializes registered hooks dictionary mapping event names to lists of handler functions.
2. register_hook(self, event_name, handler_func):
   - Registers handler for event ("onload", "refresh", "validate", "field_change").
3. trigger_event(self, event_name, form_doc, changed_field=None):
   - Executes all handlers registered for event_name in registration order.
   - Passes (form_doc) or (form_doc, changed_field) if event_name == "field_change".
   - Handlers may mutate form_doc directly (e.g. recalculating totals).
   - If a handler for "validate" raises ValueError(msg):
     Propagate exception immediately to cancel submission!
   - Returns mutated form_doc.

        def test_client_script_mutation():
    dispatcher = ClientScriptDispatcher()
    def calculate_total(doc, field):
        if field in ["quantity", "rate"]:
            doc["total"] = doc.get("quantity", 0) * doc.get("rate", 0)

    dispatcher.register_hook("field_change", calculate_total)
    doc = {"quantity": 10, "rate": 5}
    dispatcher.trigger_event("field_change", doc, changed_field="rate")
    assert doc.get("total") == 50

def test_client_script_validate_rejects():
    dispatcher = ClientScriptDispatcher()
    def validate_positive(doc):
        if doc.get("quantity", 0) <= 0:
            raise ValueError("Quantity must be positive")

    dispatcher.register_hook("validate", validate_positive)
    try:
        dispatcher.trigger_event("validate", {"quantity": -5})
        assert False, "Should raise ValueError on invalid doc"
    except ValueError as e:
        assert "Quantity must be positive" in str(e)

def test_client_script_no_handlers():
    dispatcher = ClientScriptDispatcher()
    doc = {"a": 1}
    res = dispatcher.trigger_event("onload", doc)
    assert res == doc

        

        

        

        Boss
        Differential parity oracle evaluating reference vs mobile implementation
        
not tried
        

        Write evaluate_parity_suite(test_cases, reference_engine, client_engine):
Inputs:
- test_cases: List of test input dicts:
  [{"id": str, "payload": dict, "required_stubs": [str, ...]}, ...]
- reference_engine: Callable ref(payload) returning result dict {"valid": bool, "data": dict}.
- client_engine: Dict {"evaluator": callable(payload), "installed_stubs": [str, ...]}.
        

        Parity Evaluation Rules:
For each test case:
1. Missing Stub Check:
   - Check if any stub in case["required_stubs"] is NOT in client_engine["installed_stubs"].
   - If missing stubs exist:
     Record outcome as {"id": case["id"], "verdict": "INCONCLUSIVE", "reason": f"Missing stubs: {missing_list}"}.
     (Missing stubs prevent definitive parity certification!).
2. Parity Execution:
   - If all stubs present: execute ref_res = reference_engine(payload) and client_res = client_engine["evaluator"](payload).
   - "Superset, Never Contradicting" Criterion:
     - ref_res["valid"] == client_res["valid"] AND matching data fields.
     - If matches: record {"id": case["id"], "verdict": "PASS"}.
     - If contradicts: record {"id": case["id"], "verdict": "FAIL", "reason": "Contradiction detected"}.
3. Suite Summary:
   - Total cases $N$.
   - pass_count, fail_count, inconclusive_count.
   - is_certified = (fail_count == 0 and inconclusive_count == 0 and N > 0).
4. Return dict:
   {"cases": [result_dict, ...], "pass_count": int, "fail_count": int, "inconclusive_count": int, "is_certified": bool}.

          def test_parity_pass():
    cases = [{"id": "c1", "payload": {"val": 10}, "required_stubs": ["fetch_user"]}]
    ref = lambda p: {"valid": True, "data": {"val": 10}}
    client = {
        "evaluator": lambda p: {"valid": True, "data": {"val": 10}},
        "installed_stubs": ["fetch_user"]
    }
    res = evaluate_parity_suite(cases, ref, client)
    assert res["is_certified"] is True
    assert res["pass_count"] == 1

def test_parity_inconclusive_on_missing_stub():
    cases = [{"id": "c2", "payload": {}, "required_stubs": ["geo_lookup"]}]
    ref = lambda p: {"valid": True, "data": {}}
    client = {"evaluator": ref, "installed_stubs": []} # Missing geo_lookup!

    res = evaluate_parity_suite(cases, ref, client)
    assert res["is_certified"] is False
    assert res["inconclusive_count"] == 1
    assert res["cases"][0]["verdict"] == "INCONCLUSIVE"

def test_parity_fail_contradiction():
    cases = [{"id": "c3", "payload": {}, "required_stubs": []}]
    ref = lambda p: {"valid": True, "data": {}}

    res = evaluate_parity_suite(cases, ref, client)
    assert res["is_certified"] is False
    assert res["fail_count"] == 1
    assert res["cases"][0]["verdict"] == "FAIL"

          

          Misconceptions
            

          • "Server-driven UI means rendering web pages inside a mobile WebView." SDUI renders native platform widgets (Flutter, Compose, Swift) using JSON blueprints delivered by the server; it does not use WebViews.
            • 

          • "Dynamic client scripts should use JavaScript eval() on mobile devices." Raw eval() on remote strings exposes applications to remote code execution (RCE) attacks; safe AST evaluators must be used.
            • 

          • "Missing stubs in client-side testing should just return false." Treating missing stubs as false causes spurious test failures; missing stubs indicate incomplete test environments and must be flagged as INCONCLUSIVE.
            • 

          • "The client can override server validation rules if network is offline." The mobile client must remain a strict subset of server business rules, never contradicting backend validation.
            • 

          Where it breaks
          Server-driven UI breaks down when dynamic expression evaluators allow remote code execution through unescaped eval calls, when client-script validation hooks fail to run on offline form submissions, permitting corrupted data into local SQLite databases, or when differential parity tests ignore missing stubs and grant false certifications to non-compliant mobile form implementations.
          In your real work
          Server-driven UI and dynamic forms are the answer wherever the schema changes faster than the release cycle. A backend delivers field definitions and conditional visibility rules to the client, client-side scripting validates values before submission, and a differential parity oracle checks that a mobile submission is accepted or rejected exactly as the server would. Two independent implementations of one rule set will otherwise drift, silently.
          Flash cards
          What is Server-Driven UI (SDUI)?
          An architecture where the backend delivers declarative JSON schemas defining layout and rules, while native mobile engines render widgets dynamically.
          What does depends_on specify in form schemas?
          A conditional expression that dynamically determines whether a field is visible to the user based on form state.
          Why must dynamic expressions use a safe AST subset?
          To prevent Remote Code Execution (RCE) and injection vulnerabilities that arise from raw string evaluation.
          What is the 'superset, never contradicting' parity criterion?
          Mobile clients may offer additional features (e.g. offline support), but must never contradict server validation decisions.
          Why do missing stubs make a parity test INCONCLUSIVE?
          Because the true behavior of the un-stubbed API call is unknown, making it impossible to certify whether the client passed or failed.
          What is the purpose of the client-script validate hook?
          To run client-side business logic and throw errors to block invalid form submissions before sending data to the server.
          Stop when
          You can evaluate safe AST depends_on expressions, compute dynamic form field visibility states, dispatch client-script lifecycle events, and run differential parity oracles with inconclusive stub handling.
