The story

Ravi is reconciling a day's billing. The system charged 2,431 customers, and the ledger total is off by four paise.

Four paise is nothing. Four paise is also impossible — every individual charge is correct, he checks a hundred of them by hand. Correct numbers that add up to a wrong total.

He tries the obvious thing: add them again. Same answer. He adds them in a different order, sorted by customer id instead of by time. Different answer. Off by three paise this time.

This is the moment worth stopping on. Addition is associative. $(a+b)+c = a+(b+c)$ is not a convention or a convenience; it is one of the first facts anyone learns about numbers, and it is true for integers, for rationals, for reals. Ravi's computer is adding the same 2,431 numbers and getting different totals depending on the order.

Nothing is broken. The machine is not storing his numbers. It is storing the nearest number it can represent, and 0.01 is not one of them — in binary, one hundredth is a recurring fraction exactly as one third is in decimal. Every charge is slightly wrong before any addition happens, and the order decides how those tiny errors stack.

The fix is not more precision. Doubling the precision would move the error to the fifteenth decimal place instead of the eleventh, and he would find it again next quarter with more customers. The fix is to know which operations amplify error and which do not — and, for money, not to use binary floats at all.

Say it simply

A computer stores a real number as sign, exponent and mantissa — scientific notation in binary, with a fixed budget of digits. Most numbers do not fit, so what gets stored is the nearest one that does.

That rounding is tiny: about one part in $10^{16}$ for a 64-bit double, a quantity called machine epsilon. The danger is never the single rounding. It is amplification: operations that take a small relative error and make it large.

The worst offender is cancellation — subtracting two nearly equal numbers. The leading digits agree and annihilate, leaving the error promoted to the front.

Two different words describe what can go wrong. A problem is ill-conditioned when its true answer is hypersensitive to its input. An algorithm is unstable when it adds error the problem did not require. The first is the question's fault; the second is yours.

Say it precisely

IEEE 754

A binary64 double occupies 64 bits: 1 sign $s$, 11 exponent $e$, 52 mantissa $m$. For a normal number ($1\le e\le2046$) the value is

$$(-1)^s \times 1.m_2 \times 2^{e-1023}$$

The leading 1 is implicit, buying a free 53rd bit of precision. Special cases use the reserved exponents:

$e$ $m$ meaning
0 0 $\pm0$ (two of them)
0 $\ne0$ subnormal: $0.m_2\times2^{-1022}$, gradual underflow
2047 0 $\pm\infty$
2047 $\ne0$ NaN

NaN is not equal to itself, which is the standard's way of saying "no answer", and is why x != x is a NaN test.

Machine epsilon $\varepsilon = 2^{-52}\approx2.22\times10^{-16}$ is the gap between 1.0 and the next double. An ulp (unit in the last place) is the local gap, which scales with magnitude: near $2^k$ it is $2^{k-52}$. The relative error of a correctly rounded operation is at most $\frac{\varepsilon}{2}$, so

$$\mathrm{fl}(a\circ b) = (a\circ b)(1+\delta), \qquad |\delta|\le\frac{\varepsilon}{2}$$

Rounding modes. The default is round half to even, which breaks ties towards an even last digit so that rounding errors do not accumulate in one direction. This is why round(0.5) is 0 and round(2.5) is 2 in Python — not a bug, but statistical hygiene. The standard also defines round towards zero, towards $+\infty$ and towards $-\infty$.

Cancellation and conditioning

Subtracting nearby quantities is exact at the bit level (Sterbenz: if $\frac{y}{2}\le x\le2y$ then $x-y$ is exact) — the damage is that the inputs already carried error, and the subtraction strips away the agreeing digits that were hiding it. If $x$ and $y$ each have relative error $\delta$, then $x-y$ has relative error about

$$\delta\cdot\frac{|x|+|y|}{|x-y|}$$

and the fraction blows up as $x\to y$.

The standard repairs replace the subtraction with an algebraically equal expression that has none:

Unstable Stable Why
$1-\cos x$ $2\sin^2\frac{x}{2}$ no subtraction of nearby values
$e^x-1$ expm1(x) the series is computed directly
$\ln(1+x)$ log1p(x) likewise
$\sqrt{x+1}-\sqrt{x}$ $\frac{1}{\sqrt{x+1}+\sqrt{x}}$ multiply by the conjugate
$\frac{-b\pm\sqrt{b^2-4ac}}{2a}$ $q=-\frac{b+\operatorname{sign}(b)\sqrt{D}}{2}$, roots $\frac{q}{a},\frac{c}{q}$ one root always cancels

The condition number measures how much a problem amplifies input error. For evaluating $f$ at $x$,

$$\kappa(x) = \left|\frac{x f'(x)}{f(x)}\right|$$

For subtraction $f(x)=x-y$ with $y$ fixed, $\kappa=\left|\frac{x}{x-y}\right|$, which is enormous near $x=y$ — the same statement again, now as a number.

Conditioning belongs to the problem; stability belongs to the algorithm. A stable algorithm on an ill-conditioned problem still gives a bad answer, and there is no algorithm that fixes it. That is the honest limit, and M31's condition number for matrices is the same idea.

Summation

Adding $n$ numbers naively has a worst-case error bound of $O(n\varepsilon)\sum|x_i|$: the error grows with the count. Kahan summation carries the lost low-order bits in a compensation term:

s = 0; c = 0
for x in values:
    y = x - c
    t = s + y
    c = (t - s) - y     # what was lost when y was added
    s = t

and achieves $O(\varepsilon)\sum|x_i|$ — a bound independent of $n$. The line c = (t - s) - y looks like it must be zero, and in exact arithmetic it is. It is exactly the rounding error, recovered.

Sorting by increasing magnitude before summing also helps, because it stops a large running total from swallowing small addends.

Root finding

Method Needs Order Guaranteed?
Bisection a sign change 1 (halves each step) yes
Newton $f'$, a good start 2 no
Secant two starts $\varphi\approx1.618$ no

Bisection: the interval halves, so the error after $k$ steps is $\frac{b-a}{2^k}$ — about 50 steps for full double precision, every time, with no surprises.

Newton: $x_{n+1}=x_n-\frac{f(x_n)}{f'(x_n)}$. Near a simple root the error squares, so the correct digits double each step. At a multiple root the order drops to 1, and a bad start can cycle or diverge.

Secant: replaces $f'$ with a finite difference. The order $\varphi=\frac{1+\sqrt5}{2}$ is the golden ratio, which falls out of the error recurrence $e_{n+1}\approx Ce_ne_{n-1}$.

Interpolation and Runge's phenomenon

Through $n+1$ points there is exactly one polynomial of degree $\le n$. It is tempting to conclude that more points give a better fit. For equispaced nodes this is false. Runge's function $f(x)=\frac{1}{1+25x^2}$ on $[-1,1]$ interpolated at equispaced points diverges near the ends as $n$ grows, with the error growing without bound.

The cure is the node placement. Chebyshev nodes $x_k=\cos\left(\frac{k\pi}{n}\right)$ cluster near the endpoints and make the error converge. The problem was never the degree; it was the uniform spacing.

A pinch of history

Before 1985 every manufacturer had its own floating-point format, and a program's answers changed when it moved machines. William Kahan drove the IEEE 754 standard through, earning the 1989 Turing Award; gradual underflow via subnormals was among its most contested features. Kahan's compensated summation dates from 1965.

Carl Runge published his phenomenon in 1901. Newton described his method around 1669 and Raphson simplified it in 1690; the modern iterative form is due to Simpson in 1740. The costs of getting it wrong are documented: in 1991 a Patriot missile battery at Dhahran failed to intercept because its clock accumulated a 0.34 s drift from representing 0.1 in 24 bits, and in 1992 the Vancouver Stock Exchange index had drifted from 1000 to 520 over 22 months by truncating rather than rounding on every recalculation.

Why it's true

Result 1: 0.1 is not representable. A binary fraction terminates only when its denominator is a power of two. $\frac{1}{10}=\frac{1}{2\cdot5}$ has a factor of 5, so in binary it recurs: $0.0\overline{0011}_2$. The nearest double is

$$0.1000000000000000055511151231257827021181583404541015625$$

exactly — which you can print, because the stored value is a dyadic rational and therefore has a finite decimal expansion. The same argument shows $\frac13$ recurs in decimal, which nobody finds surprising; the only novelty is which denominators are privileged.

Result 2: why cancellation promotes error. Let $\hat x = x(1+\delta_1)$ and $\hat y=y(1+\delta_2)$ with $|\delta_i|\le u$. Then

$$\hat x-\hat y = (x-y)\left(1 + \frac{x\delta_1-y\delta_2}{x-y}\right)$$

so the relative error of the difference is bounded by $u\cdot\frac{|x|+|y|}{|x-y|}$. Nothing about the subtraction is inaccurate — the factor is simply the ratio of what you started with to what survived. When $x-y$ is a thousand times smaller than $x$, the relative error is a thousand times larger, and three more digits of the answer are noise.

Result 3: Kahan's compensation recovers the exact error. Suppose $|s|\ge|y|$ and let $t = \mathrm{fl}(s+y)$. Write $t = s+y-e$ where $e$ is the rounding error. Then $t-s$ is computed exactly — this is Sterbenz's lemma, since $t$ and $s$ are within a factor of 2 — giving $y-e$. Subtracting $y$ yields $-e$... and the code stores $c=(t-s)-y=-e$, then subtracts $c$ from the next addend, feeding the lost bits back in. The algorithm works because of an exactness result, not in spite of rounding.

Result 4: Newton's order is 2. Let $r$ be a simple root and $e_n=x_n-r$. Taylor-expanding $f$ about $x_n$ and evaluating at $r$:

$$0 = f(r) = f(x_n) - e_nf'(x_n) + \frac{e_n^2}{2}f''(\xi)$$

Dividing by $f'(x_n)$ and rearranging with $x_{n+1}=x_n-\frac{f(x_n)}{f'(x_n)}$ gives

$$e_{n+1} = \frac{f''(\xi)}{2f'(x_n)}e_n^2$$

So $|e_{n+1}|\le C|e_n|^2$: the number of correct digits doubles. The hypothesis $f'(r)\ne0$ is load-bearing — at a double root $f'(r)=0$, the constant blows up, and convergence degrades to linear.

Result 5: Runge's divergence. The interpolation error is

$$f(x)-p_n(x) = \frac{f^{(n+1)}(\xi)}{(n+1)!}\prod_{k=0}^{n}(x-x_k)$$

Two factors fight. For equispaced nodes the product $\prod|x-x_k|$ is far larger near the endpoints than in the middle — by a factor that grows like $2^n$ — while $\frac{f^{(n+1)}}{(n+1)!}$ for Runge's function does not shrink fast enough to compensate, because the function has poles at $x=\pm\frac{i}{5}$ in the complex plane, close to the interval. The product wins and the error diverges. Chebyshev nodes are precisely the placement that minimises $\max\prod|x-x_k|$, flattening the term that was growing.

Oracle lab

The oracle checks float arithmetic against two independent exact references: fractions.Fraction, which is exact rational arithmetic, and decimal.Decimal, which is exact for the decimal fractions money is made of.

Neither consults the float result. Whenever they disagree with the float, the exact answers are right and the float is the approximation — which is the only way to measure an error honestly.

The mutant replaces Kahan summation with naive summation while still claiming the compensated bound, which is a real and common slip: the compensation variable is computed and then never used.

Experiment lab
Four predictions, each measured.


First, the machine's own constants. Theory says $\varepsilon=2^{-52}$ and that the gap between neighbouring doubles scales with magnitude. We find epsilon by search rather than by lookup.


Second, cancellation. Theory says the relative error of $1-\cos x$ grows like $\frac{1}{x^2}$ as $x\to0$ while $2\sin^2\frac{x}{2}$ stays at the rounding floor. We measure both against exact arithmetic.


Third, convergence orders. Bisection should need about 50 iterations for full precision whatever the problem, Newton about 5, secant in between.


Fourth, Runge. Equispaced interpolation of $\frac{1}{1+25x^2}$ should get worse with more points, and Chebyshev nodes should get better.

Where reality disagrees: the Runge table is the one that overturns an intuition. Going from degree 4 to degree 16 made the equispaced fit roughly a hundred times worse, and at degree 16 the error exceeds the full range of the function being fitted — the interpolant oscillates wildly near $\pm1$ while passing exactly through every data point. Every one of those points is fitted perfectly. The curve between them is garbage.


The cancellation table is the other one to sit with. At $x=10^{-8}$ the naive $1-\cos x$ retains essentially no correct digits, while $2\sin^2\frac{x}{2}$ — the same quantity by a trigonometric identity you learned in school — is accurate to the last bit. The difference is not precision, effort or language. It is the choice of algebraically equivalent expression.

def test_the_orders_are_what_theory_says():
    from math import sqrt
    f = lambda x: x * x - 2
    df = lambda x: 2 * x
    _, sb = bisect(f, 1.0, 2.0)
    _, sn = newton(f, df, 2.0)
    _, ss = secant(f, 1.0, 2.0)
    # bisection gains one bit a step, so it needs about 40 for 1e-12
    assert 35 < sb < 60, sb
    assert sn < 10, sn
    assert sn <= ss < sb, (sn, ss, sb)
    # Newton's measured order is 2
    errs = []
    x = 2.0
    for _ in range(6):
        errs.append(abs(x - sqrt(2)))
        x = x - f(x) / df(x)
    p = convergence_order(errs)
    assert 1.7 < p < 2.4, p
    # the secant's order is the golden ratio, about 1.618
    errs_s = []
    a, b = 1.0, 2.0
    for _ in range(8):
        errs_s.append(abs(b - sqrt(2)))
        fa, fb = f(a), f(b)
        if fa == fb:
            break
        a, b = b, b - fb * (b - a) / (fb - fa)
    ps = convergence_order(errs_s)
    assert 1.3 < ps < 1.9, ps
    assert ps < p, "the secant is slower than Newton"
    try:
        convergence_order([0.1])
        assert False, "too few errors must raise ValueError"
    except ValueError:
        pass


def test_bisection_is_guaranteed_where_newton_is_not():
    # Newton cycles forever from this start; bisection does not care
    g = lambda x: x ** 3 - 2 * x + 2
    dg = lambda x: 3 * x * x - 2
    _, steps = newton(g, dg, 0.0, max_steps=60)
    assert steps == 60, "Newton exhausts its budget without converging"
    assert abs(g(newton(g, dg, 0.0, max_steps=60)[0])) > 0.1, "and is nowhere near"
    r, s = bisect(g, -3.0, 0.0)
    assert abs(g(r)) < 1e-6, "bisection converges regardless"
    assert s < 60
    # at a DOUBLE root Newton degrades from quadratic to linear
    h = lambda x: (x - 1) ** 2
    dh = lambda x: 2 * (x - 1)
    errs = []
    x = 2.0
    for _ in range(12):
        errs.append(abs(x - 1.0))
        x = x - h(x) / dh(x)
    p = convergence_order(errs)
    assert p < 1.4, f"a double root costs the quadratic order, got {p}"

            Misconceptions
              

            • "Floating point is random or buggy." It is deterministic and specified to the bit. The same operations on the same inputs give the same answer on every conforming machine. What it is not is exact.
              • 

            • "Use more precision and the problem goes away." More precision moves the error later, it does not remove it. An ill-conditioned problem is ill-conditioned at any precision; Ravi's ledger would fail again next quarter.
              • 

            • "== on floats is always wrong." Not always. Comparing to zero after an exact operation, checking x != x for NaN, and testing for a power of two are all legitimate. What is wrong is expecting two different computations of the same quantity to agree bit for bit.
              • 

            • "Cancellation makes the subtraction inaccurate." The subtraction is usually exact. It merely exposes error that the inputs were already carrying.
              • 

            • "Kahan summation is slower, so it is not worth it." It is about four arithmetic operations instead of one, which is nothing against a memory-bound loop, and it converts an $O(n\varepsilon)$ error into an $O(\varepsilon)$ one.
              • 

            • "A higher-degree polynomial fits better." Runge's function at degree 16 on equispaced nodes has an error larger than the function itself. The node placement matters more than the degree.
              • 

            • "Newton's method always converges." It converges quadratically near a simple root given a good start. Drop any of those three and it can cycle, diverge, or crawl linearly.
              • 

            • "NaN means the computation failed." NaN propagates silently through arithmetic. A NaN at the end of a pipeline may have been born a thousand operations earlier, which is why checking early matters.
              • 

            • "0.1 + 0.2 == 0.3 is a Python quirk." It is the same in C, Java, Rust, JavaScript and on your calculator's internals. It is IEEE 754, not a language.
              • 

            Where it breaks
            The cancellation repairs are specific, not general. There is no mechanical transformation that makes an arbitrary expression stable; each one is a separate algebraic insight, which is why libraries ship expm1 and log1p as primitives rather than expecting you to derive them.
            

            Kahan summation is defeated by an optimising compiler that "simplifies" (t - s) - y to zero, which is valid for real numbers and wrong for floats. This is exactly what -ffast-math does, and it silently removes the compensation. The same flag lets the compiler reassociate additions, so a parallel reduction gives a different answer from a serial one — reproducibility and performance are genuinely in tension here.
            

            Decimal is exact for decimal fractions and no more. One third is as unrepresentable in decimal as one tenth is in binary, so Decimal(1)/3 still rounds. Decimal is right for money because money is decimal, not because decimal is more accurate.
            

            Subnormals preserve the property that x - y == 0 implies x == y, but on many processors they are handled in microcode and run one to two orders of magnitude slower, which is why numerical code sometimes sets flush-to-zero and accepts the loss.
            

            Newton's method on a multiple root loses its quadratic order, and the usual fix — applying Newton to $\frac{f}{f'}$ — reintroduces cancellation. And interpolation is not the same as approximation: Chebyshev nodes fix Runge, but if your data has noise, fitting a high-degree polynomial through every point is the wrong goal entirely. Use a lower-degree least-squares fit or a spline.
            

            Finally, almost none of this appears in testing. A float bug produces an answer that is slightly wrong, passes every smoke test, and surfaces as four paise six months later.
            In your real work
            The money rule is absolute and comes first: currency is stored in integer minor units — paise, cents — or in a decimal type, never in a binary float. Every payments system, ledger and tax calculation does this, and the Vancouver index is what happens when it does not.
            

            Accumulating error shows up anywhere a loop runs long. Physics integrators, running averages over a metrics stream, and any total += x over millions of rows are the usual places; a running mean computed with Welford's algorithm rather than by summing then dividing is the same instinct as Kahan's.
            

            Tolerance comparisons need both an absolute and a relative term — abs(a-b) <= atol + rtol*abs(b) — because a pure relative test fails near zero and a pure absolute test fails at large magnitudes. Every numerical test suite you write will need this.
            

            In machine learning the same ideas wear different names: the log-sum-exp trick subtracts the maximum before exponentiating to avoid overflow, cross-entropy is computed from logits rather than from probabilities to avoid log(0), and gradient clipping is error-propagation control. Mixed-precision training keeps a float32 master copy of the weights precisely because repeatedly accumulating small float16 updates into a large value loses them — Ravi's problem, on a GPU.
            

            And when a result looks wrong, the question to ask is the one that splits the blame: is the problem ill-conditioned, or is my algorithm unstable? The first means no algorithm will save you and the question needs reformulating. The second is a bug you can fix.
            Flash cards
            Why is 0.1 not exactly representable?
            A binary fraction terminates only when the denominator is a power of two. One tenth has a factor of 5, so it recurs in binary just as a third recurs in decimal.
            What is machine epsilon, and how does it differ from an ulp?
            Epsilon is the gap between 1.0 and the next double, 2^-52. An ulp is the LOCAL gap, which scales with magnitude: near 2^k it is 2^(k-52).
            What is catastrophic cancellation?
            Subtracting two nearly equal numbers. The agreeing leading digits annihilate and the pre-existing error is promoted to the front. The subtraction itself is usually exact.
            Give three stable replacements for cancelling expressions.
            1 - cos x becomes 2 sin^2(x/2); e^x - 1 becomes expm1; log(1+x) becomes log1p. Also the conjugate trick for sqrt(x+1) - sqrt(x).
            What is the difference between conditioning and stability?
            Conditioning is a property of the PROBLEM — how much it amplifies input error. Stability is a property of the ALGORITHM — whether it adds error the problem did not require.
            Why does Kahan summation work?
            (t - s) - y is computed exactly by Sterbenz's lemma, so it recovers the rounding error, which is then fed back into the next addend. The error bound becomes independent of n.
            Give the convergence orders of bisection, Newton and secant.
            Bisection 1 (halves each step, ~50 for full precision, always converges); Newton 2 (digits double, no guarantee); secant the golden ratio, about 1.618.
            When does Newton's method lose its quadratic order?
            At a multiple root, where f'(r) = 0. Convergence degrades to linear.
            What is Runge's phenomenon?
            Interpolating 1/(1+25x^2) at equispaced nodes on [-1,1] DIVERGES near the endpoints as the degree grows. Chebyshev nodes, which cluster at the ends, converge.
            Why does money use decimals rather than floats?
            Money is defined in decimal units and must be exact. Binary floats cannot represent 0.01, so the error accumulates across many transactions into a real discrepancy.
            How should floats be compared?
            With a mixed tolerance, abs(a-b) <= atol + rtol*abs(b). A purely relative test fails near zero; a purely absolute one fails at large magnitudes.
            Stop when
            You can explain why 0.1 is not 0.1 without saying "floats are weird", you can look at an expression and point to the subtraction that will cancel, you can state whether a bad answer is the problem's fault or the algorithm's and justify it with a condition number, you can write Kahan summation from memory and say why the compensation line is not zero, you can pick between bisection and Newton by naming what each guarantees, you can explain Runge's phenomenon to someone who thinks more points must be better, you pass the boss exercise without hints, and you never again store a currency amount in a float.
