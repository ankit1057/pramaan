The story

In 2008, when Android 1.0 launched, mobile user interfaces were constructed using the classic imperatively driven View system. Every button, text view, and layout was an object in a heavy mutable class hierarchy (android.view.View), configured through XML layout files and updated by imperative mutations (findViewById() followed by setText() and setVisibility()). For over a decade, this imperative model dominated Android development. However, as mobile apps grew complex, managing mutable view state became a primary source of UI bugs: views frequently fell out of sync with underlying models, views leaked Activity contexts, and deeply nested layout passes caused severe frame drops. In 2021, Google released Jetpack Compose, a modern declarative UI toolkit that reimagined Android UI from the ground up. Instead of mutating existing views, developers write idempotent composable functions that describe the UI for a given state; when state changes, the Compose runtime automatically executes intelligent recomposition, recalculating and redrawing only the exact widgets that changed.

Say it simply

In Android development, there are two ways to build user interfaces: the traditional View system and modern Jetpack Compose. In the traditional View system, you design screens in XML files and manually update buttons and text boxes using code. In Jetpack Compose, you write Kotlin functions with the @Composable annotation that describe what the screen should look like for a given state. When data changes (like a score updating), Compose automatically "recomposes" only the parts of the screen that depend on that data, skipping everything else. This makes screens much faster to build, easier to test, and eliminates bugs where the screen displays outdated information.

Say it precisely

Android UI architectures contrast the imperative View system with declarative Jetpack Compose: 1. The Classic View System Pipeline: - Three recursive passes across the view hierarchy: - Measure: Parent views query children (measure()) with MeasureSpec constraints (EXACTLY, AT_MOST, UNSPECIFIED). - Layout: Parent assigns position coordinates (layout(l, t, r, b)). - Draw: Canvas draws background, self, and children (onDraw(canvas)). - Deep hierarchies trigger exponential layout measurement passes (especially with nested LinearLayout using layout_weight).

  1. RecyclerView and DiffUtil: - RecyclerView recycles offscreen ViewHolder instances to bound memory consumption. - DiffUtil uses Eugene Myers' $O(ND)$ difference algorithm to compute minimal edit scripts (notifyItemInserted, notifyItemRemoved, notifyItemMoved), enabling smooth item animations.

  2. Jetpack Compose Architecture: - Composition: The runtime executes @Composable functions, emitting an in-memory Slot Table representing the UI tree. - Recomposition: When observed state (State<T>) changes, Compose re-executes only the composables that read that state. - Stability and Skipping:

    • A composable is skippable if all its parameters are stable (primitives, immutable data classes).
    • If parameters are unstable (e.g. standard List<T>), Compose re-executes the composable on every recomposition pass!

  3. State Hoisting & Side Effects: - State hoisting pattern: move state up to make composables stateless and testable (value: T, onValueChange: (T) -> Unit). - Side-Effect APIs:

    • LaunchedEffect(key): Launches a coroutine bound to the composable lifecycle; cancels and restarts if key changes.
    • DisposableEffect(key): For setup and cleanup (e.g. registering/unregistering broadcast listeners).
    • rememberSaveable: Survives Activity recreation across configuration changes (e.g. screen rotation).

Why it's true

To understand why Compose's Stability and Skipping mechanism is critical for 120 FPS performance, examine what happens during recomposition:

@Composable
fun ContactRow(user: User, onCall: () -> Unit) {
  Text(user.name)
  Button(onClick = onCall) { Text("Call") }
}

If the parent screen recomposes (e.g. a timer ticks in the top bar), Compose checks whether ContactRow can be skipped: 1. Does user equal the previous user instance? 2. Are all types in User proven stable?

If User is a plain data class containing a standard Kotlin val tags: List<String>, the Compose compiler marks User as unstable! Why? Because standard Kotlin List is an interface; a caller could pass a mutable ArrayList upcast to List, mutating items under the hood without changing the list reference. Because Compose cannot guarantee immutability, it cannot safely skip ContactRow, forcing the entire row to re-execute on every single frame! Wrapping collections in ImmutableList or annotating classes with @Immutable restores skipping, eliminating redundant recompositions, conserving main-thread execution time, and preventing jank across complex mobile user interfaces.

Write classify_composable_stability(composable_name, parameter_specs):
Inputs:
- composable_name: String name of the composable function.
- parameter_specs: List of dicts representing function parameters:
  [{"name": str, "type": str, "is_var": bool, "has_mutable_fields": bool}, ...]


Stability Rules (Compose Compiler Specification):
A parameter is Stable if:
1. is_var is False (val, not var).
2. type is a primitive ("Int", "Float", "Double", "Boolean", "String", "Function").
3. OR type is a known immutable container ("ImmutableList", "ImmutableSet").
4. Unstable types:
   - Any parameter with is_var is True.
   - Any interface collection ("List", "Set", "Map" without "Immutable" prefix).
   - Any class with has_mutable_fields is True.


A composable is Skippable if and only if ALL its parameters are stable.
Return dict:
{"composable": composable_name, "is_skippable": bool, "unstable_parameters": [str, ...]}.

Generate a minimal list of update operations transforming old_list into new_list:

   - Record {"op": "MOVE", "item": item, "from_index": old_idx, "to_index": new_idx}.
4. Total operations count $M$.
5. Return dict:
   {"operations": [op_dict, ...], "operations_count": len(operations)}.

        Write a class LaunchedEffectSimulator:
Simulate Jetpack Compose's LaunchedEffect(key) coroutine lifecycle:
1. __init__(self, key, effect_coroutine):
   - Stores current key.
   - Tracks active_job = True.
   - Tracks total launched count (launch_count = 1).
   - Tracks cancellation count (cancel_count = 0).
2. on_recompose(self, new_key):
   - If new_key == self.key:
     - Key has NOT changed: active job continues running undisturbed!
   - If new_key != self.key:
     - Key changed!
     - Cancel previous job: self.cancel_count += 1, self.active_job = False.
     - Update self.key = new_key.
     - Launch new job: self.active_job = True, self.launch_count += 1.
3. on_dispose(self):
   - Composable left composition!
   - If self.active_job is True:
     self.active_job = False, self.cancel_count += 1.

          Misconceptions
            

          • "Jetpack Compose and traditional Views cannot be used together in the same app." ComposeView allows embedding Compose inside traditional XML Views, and AndroidView allows embedding traditional Views (like MapView) inside Compose.
            • 

          • "Passing a standard Kotlin List to a Composable allows it to skip recomposition." Standard List is an unstable interface in Compose; Compose cannot guarantee immutability and will re-execute the Composable on every recomposition unless wrapped in ImmutableList.
            • 

          • "LaunchedEffect(Unit) will rerun on every recomposition." LaunchedEffect with a constant key like Unit runs exactly once when entering composition and will never restart during recomposition.
            • 

          • "Nested LinearLayout with layout_weight has zero performance penalty." Using layout_weight forces the parent view to measure its children twice, causing exponential 2^N measure passes in deeply nested hierarchies.
            • 

          Where it breaks
          Android UI breaks down when unstable collection parameters force Jetpack Compose to re-execute entire screen hierarchies on every frame, causing noticeable animation stutter, when deeply nested View hierarchies trigger exponential measure passes that freeze the main thread, or when LaunchedEffect coroutines run infinite loops without key cancellation, triggering memory leaks and duplicate network requests.
          In your real work
          Android UI architecture governs how interaction actually feels. Jetpack Compose provides stable, skippable composables so an unrelated state change does not recompose a whole screen, DiffUtil animates list updates smoothly as sensor readings arrive, and LaunchedEffect tied to the lifecycle cancels a sync job cleanly when the user navigates away mid-request.
          Flash cards
          What are the three passes of the classic Android View system?
          Measure (determining size), Layout (positioning children), and Draw (rendering pixels to Canvas).
          What is recomposition in Jetpack Compose?
          The process of re-executing composable functions whose observed state has changed to update the UI tree.
          Why does passing a standard List cause recomposition jank?
          Standard List is considered unstable by the Compose compiler, preventing the composable from skipping recomposition.
          How does DiffUtil optimize RecyclerView updates?
          By calculating the minimal edit operations (insertions, deletions, moves) between lists using Myers' diff algorithm instead of redrawing all items.
          What does LaunchedEffect(key) do when key changes?
          It cancels the currently running coroutine job and launches a new coroutine with the updated key.
          What is state hoisting in Jetpack Compose?
          Moving state to a caller to make a composable stateless, reusable, and easy to unit test.
