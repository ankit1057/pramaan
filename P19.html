The story

On July 20, 1969, during the Apollo 11 lunar descent, the Apollo Guidance Computer (AGC) was suddenly overwhelmed by radar data, triggering repeated 1202 and 1201 alarm codes three minutes before touchdown. Rather than crashing or rebooting, the AGC preserved life-critical thruster control and landed Neil Armstrong and Buzz Aldrin safely on the Moon. This triumph was engineered by Margaret Hamilton, Director of the Software Engineering Division at the MIT Instrumentation Laboratory. Hamilton had pioneered asynchronous executive scheduling, priority-based job preemption, and rigorous software verification, coining the term "software engineering" to demand that the craft of writing code receive the same scientific rigor and respect as hardware engineering.

In the decades that followed, the software industry struggled with what Edsger Dijkstra called the "software crisis"—the reality that software systems routinely exceeded budgets, slipped schedules, and failed catastrophically in production. In 1975, Fred Brooks published The Mythical Man-Month, proving that adding manpower to a late software project only makes it later due to combinatorial communication overhead. In the late 1990s and early 2000s, Kent Beck, Ward Cunningham, and Martin Fowler launched Extreme Programming and Test-Driven Development (TDD), arguing that high-confidence engineering requires fast feedback loops, automated testing pyramids, refactoring to eliminate technical debt, and continuous integration. Today, modern engineering teams manage massive distributed and mobile applications using Git DAG workflows, blast radius call-graph analysis, and blameless postmortems, recognizing that regression safety and architectural discipline are the defining qualities of world-class engineering.

Say it simply

Software engineering is the application of systematic scientific principles, architectural patterns, and disciplined processes to build, test, and maintain software over long periods of time. Writing code is only one small part of engineering: you must turn vague user requirements into clear acceptance criteria, decouple components so that changing one piece doesn't break another, track changes using Git commit graphs, and verify behavior with automated testing pyramids. You proactively manage technical debt, isolate side effects through dependency injection, analyze the blast radius of every pull request before shipping, and respond to live incidents with blameless postmortems that strengthen systems against future failure.

Say it precisely

Building software is a lot like building a giant city out of LEGOs with a hundred of your friends. You need rules so you don't accidentally knock over someone else's building!

  1. LEGO Connections (Coupling and Cohesion): - Good LEGOs: Every piece has one clear job and connects neatly to others. If you want to change a blue block to a red block, you just pop it out and swap it. - Bad LEGOs (Tangled Code): Imagine if you glued the blocks together, wrapped them in string, and painted over them. If you try to pull one block out, the whole tower comes crashing down! We call this "tight coupling," and we try very hard to avoid it.

  2. The Magic Diary (Git and Version Control): When many people write code together, they use a magic time-travel diary called Git. Every time you finish a page, you save it. If you make a terrible mistake tomorrow, you can easily turn the pages back to yesterday when everything worked perfectly! If two friends write two different endings to the same story, the magic diary looks back to where they split up, and carefully stitches both endings together.

  3. The Robot Food Pyramid (Testing): You have to check your work constantly so the robots don't get confused. - Tiny Tests (Vegetables): You write lots and lots of these. They are super fast and only check one tiny thing, like "Does 2 + 2 equal 4?" - Medium Tests (Meat): You write a few of these. They check if two big LEGO pieces fit together nicely. - Giant Tests (Dessert): You write very few of these. They check the entire city all at once, from top to bottom. They are very slow, so you don't want to run them too often!

  4. The Domino Effect (Blast Radius): If you push over one domino, how many other dominoes will fall? Before you change a single piece of code, you have to look at all the connections and figure out the "blast radius." If pushing your tiny domino accidentally knocks over the giant bank domino, you need to be extremely careful!

  5. The Squeaky Toy Rule (Hyrum's Law): Imagine a factory makes a toy robot, and by total accident, the robot makes a funny squeaky noise. The factory tries to fix the squeak, but thousands of kids cry because the squeak was their favorite part! In software, if your code does something accidentally, people will eventually rely on it, and it becomes almost impossible to take away.

Why it's true

Why do we need all these rules? Because building software is incredibly messy, and tiny mistakes can cause huge disasters!

Imagine a friend decides to "fix" the way doors open in your LEGO city. But they didn't check the domino effect (the blast radius), and their fix accidentally makes all the windows fall out of the buildings! By using the magic diary (Git) and writing tiny tests, the computer will instantly yell, "Wait! You broke the windows!" before the broken doors ever reach the real world.

Also, when things do go wrong (and they always do!), engineers have a special rule called "Blamelessness." If a giant tower falls over, we never yell at the person who knocked it down. We know it was an accident! Instead, we ask, "Why was the tower so wobbly in the first place? How can we make it stronger so the next person doesn't knock it down?" By focusing on building safer towers instead of blaming friends, we build amazing, strong software that everyone trusts.

          def test_transitive_blast_radius():
    analyzer = BlastRadiusAnalyzer()
    # A -> B -> C -> D
    analyzer.add_call("A", "B")
    analyzer.add_call("B", "C")
    analyzer.add_call("C", "D")

    assert blast_d == {"C", "B", "A"}
    
    # Modifying B impacts only A
    assert analyzer.compute_blast_radius("B") == {"A"}

def test_component_instability_metric():
    analyzer = BlastRadiusAnalyzer()
    # Ca = 4 (many incoming), Ce = 1 (few outgoing) -> I = 1 / 5 = 0.2 (stable)
    assert analyzer.compute_instability("CoreModule", afferent=4, efferent=1) == 0.2
    
    # Ca = 0, Ce = 5 -> I = 5 / 5 = 1.0 (maximally unstable)
    assert analyzer.compute_instability("UILeaf", afferent=0, efferent=5) == 1.0
    assert analyzer.compute_instability("Isolated", afferent=0, efferent=0) == 0.0

def test_safe_change_against_critical_symbols():
    analyzer = BlastRadiusAnalyzer()
    analyzer.add_call("CheckoutUI", "OrderService")
    analyzer.add_call("OrderService", "PaymentGateway")
    analyzer.add_call("AdminUI", "AuditLogger")
    
    critical = {"CheckoutUI", "OrderService"}
    
    # Changing PaymentGateway impacts OrderService and CheckoutUI -> UNSAFE
    assert not analyzer.is_safe_change("PaymentGateway", critical)
    
    # Changing AuditLogger impacts AdminUI -> SAFE (no critical symbols affected)
    assert analyzer.is_safe_change("AuditLogger", critical)

          

          Misconceptions
            

          • "Good code requires writing unit tests for every single private method and line of code." High-leverage engineering tests public observable contracts rather than private implementation details. Testing private methods creates brittle coupling between test suites and internal structure, causing tests to break during safe refactorings even when behavior is unchanged.
            • 

          • "More process (e.g. strict daily Scrum rituals, story points, velocity charts) automatically leads to higher software quality." Processes and rituals can easily devolve into performative cargo cults. Real software engineering focuses on fast technical feedback loops, automated CI verification, short trunk-based branches, and blameless postmortems rather than bureaucratic tracking.
            • 

          • "SOLID principles must be followed dogmatically at all times without exception." Overzealous application of SOLID (such as excessive Single Responsibility breakdown creating hundreds of tiny single-method classes, or gratuitous interfaces for classes that will only ever have one implementation) introduces accidental complexity and indirection that impairs maintainability.
            • 

          • "A postmortem's primary purpose is to identify which engineer made the mistake that caused the production outage." Effective postmortems are strictly blameless. Attributing incidents to individual human error guarantees engineers will hide mistakes. Blameless postmortems treat human error as a symptom of underlying systemic defects, such as missing linters, absent canary rollouts, or unmonitored invariants.

          Where it breaks
          Software engineering principles break or encounter severe friction in several predictable scenarios:
1. Early-Stage Disposable Prototyping: In seed-stage exploratory prototypes or hackathons where the problem domain is not yet understood, spending days constructing comprehensive DI containers, 100% test coverage pyramids, and abstract interfaces is wasted effort if the code will be discarded within 48 hours.
2. Microservice Proliferation ("Distributed Monoliths"): Splitting a small engineering team across dozens of microservices before domain boundaries stabilize leads to severe network latency, distributed transaction nightmares, and complex multi-repo coordination overhead that outweighs any modularity benefits.
3. Flaky Test Cascades: As test suites grow into the tens of thousands, poorly written integration tests that depend on system clocks, unseeded random generators, or remote network endpoints become flaky, eroding developer trust in CI and leading engineers to ignore test failures.
          In your real work
          Software engineering practices form the backbone of industrial production systems:
- Mobile CI/CD Pipelines: Fastlane, GitHub Actions, and Google Cloud Build automate static analysis, linting, unit test execution, and deployment to Google Play Internal App Sharing and Firebase App Distribution.
- Trunk-Based Development with Feature Flags: Engineers merge small, frequent commits into the main trunk, hiding incomplete features behind runtime feature flags (LaunchDarkly, Firebase Remote Config) to eliminate merge hell.
- Site Reliability Engineering (SRE) and Blameless Postmortems: Production incidents trigger automated PagerDuty rotations, severity tiering (P0/P1), mitigation runs, and blameless postmortem documents with concrete corrective action items tracked in issue trackers.
          Flash cards
          What is afferent vs efferent coupling and the instability metric?
          Afferent coupling (Ca) measures incoming dependencies, efferent coupling (Ce) measures outgoing dependencies. Instability I = Ce / (Ca + Ce), where 0 is maximally stable and 1 is maximally unstable.
          What is a Git merge-base?
          The Lowest Common Ancestor (LCA) commit between two branch heads in the Git commit Directed Acyclic Graph (DAG), used as the base for three-way merging.
          What is the Testing Pyramid?
          A software verification model recommending a large base of fast isolated unit tests (~70%), a medium layer of integration tests (~20%), and a small top layer of end-to-end tests (~10%).
          What is Hyrum's Law?
          The empirical law stating that with enough users of an API, every observable system behavior (intended or not) will be depended upon by someone, making changes risky.
          What is blast radius in software architecture?
          The set of all upstream components, services, or modules transitively affected when a specific symbol or service is modified or fails.
          What is the core philosophy of a blameless postmortem?
          Treating human error as a symptom of systemic and architectural failure rather than personal incompetence, focusing on corrective actions and safeguard mechanisms.
