The story

In 1974, MIT computer scientist Barbara Liskov published a landmark paper introducing CLU, the first programming language to formalize Abstract Data Types (ADTs). Before Liskov's work, structured programming languages exposed internal record representations; if an engineer wanted to store a set of customer records, client code directly manipulated raw pointers and internal linked list nodes. When the underlying data structure was modified to improve search performance, external calling code across the entire organization broke catastrophically. Liskov proved that software components must encapsulate private state behind an immutable public contract of operations, establishing the Liskov Substitution Principle (LSP).

A decade later in 1986, Bertrand Meyer introduced Design by Contract in the Eiffel programming language, demonstrating that software reliability is rooted in Hoare logic: every method constitutes an enforceable legal contract with preconditions, postconditions, and class invariants. Later in 2009, British computer scientist Tony Hoare stood before an auditorium of software engineers and issued a historic public apology for inventing the null reference in ALGOL W in 1965, calling it his "billion-dollar mistake." Hoare explained that the lure of designing a pointer that points to nothing was irresistible, but it spawned decades of catastrophic vulnerabilities, null pointer exceptions, and unhandled edge cases. Modern computer science responded by replacing fragile inheritance with compositional protocols, and unstructured nulls with explicit algebraic Result types.

Say it simply

Abstraction is the art of hiding internal machinery behind clean, reliable controls, like driving a car using only the steering wheel and pedals without having to know fuel injection timing. In software, we use classes to bundle data and protect rules called invariants—facts that must always stay true, like a bank balance never turning negative without an authorized overdraft. Instead of letting programs crash unpredictably or returning dangerous empty values that trigger crashes far away, resilient software uses contracts and explicit Result types that make errors impossible to overlook.

Say it precisely

The formal theory of software abstraction, type systems, and error handling is specified by:

  1. Abstract Data Types (ADTs) & Class Invariants: An ADT is defined by an algebraic specification $(\Sigma, E)$ where $\Sigma$ is the signature of operations and $E$ is the set of behavioral equations. A class invariant $\mathcal{I}(S)$ is a boolean predicate over state $S$ that must satisfy: $$\{\mathcal{I}(S) \wedge \text{Pre}_m\} \quad m(S) \quad \{\mathcal{I}(S') \wedge \text{Post}_m\}$$ for every public method $m$. If an operation threatens to violate $\mathcal{I}(S)$, execution must be rejected before state mutation occurs.

  2. The Four Kinds of Polymorphism (Cardelli & Wegner): - Subtype Polymorphism (Inclusion): An instance of subtype $S$ can substitute for supertype $T$ ($S <: T$). By the Liskov Substitution Principle: $$\forall x: T, \phi(x) \implies \forall y: S, \phi(y)$$ - Parametric Polymorphism: Functions or data types operate uniformly over generic type variables without regard to concrete types ($\Lambda \alpha. \lambda x: \alpha. x$). - Ad Hoc Polymorphism (Overloading): A single function identifier exhibits distinct, non-uniform implementations chosen at compile-time or runtime based on argument types. - Coercion Polymorphism: The language runtime or compiler automatically promotes a value of one type into another (e.g. promoting integer $4$ to float $4.0$ during floating-point addition).

  3. Composition Over Inheritance: Inheritance couples subclasses to superclass implementation details (the fragile base class problem). Composition decouples behavior by delegating tasks to injected interface implementations, preserving encapsulation boundaries.

  4. Error Handling Models: - Exceptions: Asynchronous non-local jumps unwinding the call stack. They bypass function signatures, making error paths invisible unless explicitly documented. - Result Types: Monadic algebraic types $\text{Result}\langle T, E \rangle = \text{Ok}(T) \mid \text{Err}(E)$ forcing calling code to handle failure paths via pattern matching or monadic chaining (map, flat_map).

Why it's true

Understanding why modern software engineering overwhelmingly favors composition over inheritance and algebraic Result types over unchecked exceptions requires examining how large distributed systems fail. During the 1990s, object-oriented software dogma encouraged deep inheritance hierarchies (e.g., CustomSpecializedSecureValidatedStringStream extending five ancestral classes). In practice, deep inheritance hierarchies create the fragile base class problem: a subtle optimization or bug fix applied to a parent class silently invalidates undocumented internal invariants relied upon by dozens of derived subclasses, triggering cascading regressions across the codebase.

Furthermore, traditional exceptions introduce invisible, non-local control flow jumps. When a function deep inside a call stack throws a runtime exception, the execution frame immediately aborts, unwinding through intermediate callers that may fail to release locks, close database connections, or rollback in-flight transactions. Algebraic Result types ($\text{Ok}(T) \mid \text{Err}(E)$) restore mathematical determinism to error handling. By encoding failure directly into the function's return type signature, the compiler or static analyzer forces the caller to explicitly match and handle both success and failure cases. Errors cease to be unpredictable catastrophic interruptions; they become ordinary, well-typed values that flow predictably through functional composition pipelines.

    assert r.is_ok() is False
    assert r.is_err() is True

    assert r2.is_err() is True

    def safe_div(x):
        if x == 0: return Result.err("div_zero")
        return Result.ok(100 // x)
        
    assert Result.ok(20).flat_map(safe_div).unwrap() == 5
    assert Result.ok(0).flat_map(safe_div).is_err() is True

          Misconceptions
            

          • "Inheritance is primarily meant for code reuse." Inheritance establishes a strict semantic 'is-a' subtyping relationship (LSP). Using inheritance purely for code reuse causes tight coupling and fragile base class defects; composition is preferred.
            • 

          • "Catching generic 'Exception' is good defensive programming." Catching base Exception suppresses critical bugs, keyboard interrupts, and memory errors, turning fail-fast bugs into silent, lingering data corruption.
            • 

          • "Static types eliminate all software bugs." Type systems verify structural and representation invariants at compile-time, but cannot prevent high-level semantic bugs, concurrency deadlocks, or algorithmic errors.
            • 

          • "Classes and encapsulation require private keywords enforced by the compiler." Encapsulation is an architectural boundary pattern; languages like Python enforce encapsulation via convention (_leading_underscore) and property descriptors rather than strict compiler locks.
            • 

          Where it breaks
          Abstraction barriers break down when leaky abstractions force client code to understand internal implementation details, such as an ORM abstraction forcing developers to optimize SQL join generation manually. Furthermore, class invariants fail when external code bypasses encapsulation via reflection, pointer casting, or direct shared-memory mutation, invalidating correctness guarantees in multithreaded runtimes.
          In your real work
          Abstract data types and Result error models govern modern system programming in Rust, TypeScript, and Go. Production payment gateways (Stripe), cloud APIs (AWS SDKs), and database drivers utilize explicit Result types and strict class invariants to prevent partial transaction failures and eliminate unhandled runtime null pointer exceptions.
          Flash cards
          What is an abstract data type (ADT)?
          A data type defined by its behavior (operations and contracts) from the point of view of a user, independent of implementation.
          What is the Liskov Substitution Principle (LSP)?
          If S is a subtype of T, objects of type T may be replaced with objects of type S without altering the correctness of the program.
          What is the difference between Subtype and Parametric polymorphism?
          Subtype polymorphism relies on subtyping and dynamic dispatch; parametric polymorphism allows generic code across arbitrary type variables.
          Why is composition preferred over inheritance?
          Composition avoids the fragile base class problem, loose couples components, and allows flexible behavior swapping at runtime.
          What is a class invariant?
          A condition that must always be true for every valid instance of a class, preserved before and after every public method invocation.
          How do Result types improve on exceptions?
          Result types make failure paths explicit in the function signature, forcing callers to handle errors at compile-time.
          Stop when
          You can explain the four kinds of polymorphism, implement ADTs with class invariants, design monadic Result types for safe error handling, and favor composition over inheritance.
